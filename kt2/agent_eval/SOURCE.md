# Eval-сет агента: Junkie

В MVP наш сервис диагностирует поискового агента по личному архиву **Junkie** соседней команды курса (Гринюк И., Кривова М., Островенко Е., Степанов Ю.).

- Репозиторий: https://github.com/qrvmil/junkie
- Ветка: `kt2-gold-consistency`, закреплённый коммит [`8f890da7a2e0f978eaf2ae74bf4b448334a420fb`](https://github.com/qrvmil/junkie/tree/8f890da7a2e0f978eaf2ae74bf4b448334a420fb)
- Их design doc с описанием набора, метрик и разметки: [design-doc.md](https://github.com/qrvmil/junkie/blob/8f890da7a2e0f978eaf2ae74bf4b448334a420fb/design-doc.md), разделы 7–8

Отложенную часть Junkie (в их ветке `kt2-gold-consistency` она зашифрована) мы не открываем и не используем.

## Как мы используем этот набор

1. **Запросы к агенту и эталон агента.** Каждый кейс нашего eval-сета сервиса начинается с кейса Junkie: запрос, история и фикстура берутся оттуда, эталонный вид шагов берётся из `expected`, `gold_steps` и `expected_calls`. Эти поля видит только оценщик, сервису они не передаются.
2. **Проверка чистого агента.** Перед внесением поломки агент без поломки должен пройти кейс Junkie минимум в 4 из 5 прогонов. Иначе кейс исключается из прогона: сбой есть и без нашей поломки. Исходный файл не меняется.
3. **Контрольный набор после MVP.** Когда появится автопатч, весь `dev.jsonl` станет набором, на котором проверяем, что исправление не ухудшило агента.

Своих правок в разметку Junkie не вносим. Найденные ошибки разметки передаём их команде.
